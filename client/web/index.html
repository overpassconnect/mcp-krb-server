Machine provisioning

Set your workstation up for Kerberos single sign-on against __REALM__.

Linux Windows macOS Artifacts

Linuxdefault

Enrols the machine in FreeIPA and installs the MCP bridge. After this you get a Kerberos ticket at login, and ssh works with no password anywhere in the realm. Ask whoever runs FreeIPA to run ipa host-add yourbox.__DOMAIN__ --random first: it prints the one-time password you paste below, and it is good for one enrolment only.

If /etc/ipa/default.conf already exists the machine is enrolled: skip the enrolment entirely and use the second block, which installs the bridge only.

Case 1: the machine is not enrolled yet

cd "$(mktemp -d)"
curl --proto '=https' --tlsv1.2 -fsS __BASE__/setup.sh -o setup.sh

sudo sh setup.sh \
    --base-url __BASE__ \
    --mcp-url __MCP_URL__ \
    --hostname=<the FQDN IT gave you> \
    --server=__KDC__ \
    --domain=__DOMAIN__ \
    --realm=__REALM__ \
    --password='<OTP>' \
    --unattended

Case 2: the machine is already enrolled

cd "$(mktemp -d)"
curl --proto '=https' --tlsv1.2 -fsS __BASE__/install-bridge.sh -o install-bridge.sh

sudo sh install-bridge.sh \
    --base-url __BASE__ \
    --mcp-url __MCP_URL__ \
    --managed

Both blocks download the script to a file and then run it, instead of piping curl into sh, so a truncated or interrupted download cannot half-execute as root. --proto '=https' pins the transfer to HTTPS so a redirect cannot silently downgrade it to plaintext.

TLS is the whole of the assurance on these bytes. There is no signature and no checksum file to verify. Once the machine is enrolled the scripts pin their own downloads to the realm CA at /etc/ipa/ca.crt and warn loudly if that pin ever falls back to the public trust store, but the first fetch above is ordinary public-CA TLS. Whoever controls the host serving these files decides what runs as root here: SECURITY.md [SC1]. If that is in your threat model, ship a signed package from an internal repo in your base image instead.

Extras: --skip-mcp enrols in FreeIPA only, leaving the bridge for later. Drop --managed from the second block to install the bridge without registering it machine-wide; the script then prints the claude mcp add line to run as yourself. Drop --unattended from the first block if you would rather confirm the enrolment interactively.

other platforms

Windows 11

Windows' built-in ssh.exe cannot read a Kerberos ticket, so the client runs inside WSL2. Open PowerShell as Administrator: installing the WSL distro needs it. If a distro already exists that step is skipped, but start elevated anyway so the run does not stop halfway.

Kerberos SSH only

One file, nothing else to download. This is what most people want. The realm values below are already filled in for you, so the only thing to edit is your username.

# Run PowerShell as Administrator.
$base = "__BASE__"
iwr -useb "$base/setup.ps1" -OutFile setup.ps1

.\setup.ps1 -IpaUser <your-ipa-username> `
    -Domain __DOMAIN__ -Realm __REALM__ -Kdc __KDC__ `
    -SkipVSCode

Afterwards, in a new terminal: wsl kinit <your-ipa-username>@__REALM__, then wslssh host.__DOMAIN__. Your existing ssh, keys, host aliases and known_hosts are left untouched: the script adds wslssh rather than hijacking ssh. Tickets last 24 hours and renew with wsl kinit -R.

With VS Code Remote-SSH

Drop -SkipVSCode and the script also points VS Code's remote.SSH.path at a dispatcher, so *.__DOMAIN__ goes through WSL and every other host keeps using the native Windows ssh. One profile, both worlds. This is the only step that needs JsoncEdit.ps1, so either put that file next to setup.ps1 or pass -BaseUrl and let the script fetch it.

# Run PowerShell as Administrator.
$base = "__BASE__"
iwr -useb "$base/setup.ps1" -OutFile setup.ps1

.\setup.ps1 -IpaUser <your-ipa-username> `
    -Domain __DOMAIN__ -Realm __REALM__ -Kdc __KDC__ `
    -BaseUrl __BASE__

Optional: the MCP bridge

Only if you have been asked to run it. Add -McpUrl __MCP_URL__ -CaSha256 __CA_SHA256__ to either command above, and -BaseUrl __BASE__ as well only to the first one: the second already passes -BaseUrl, and PowerShell refuses a parameter given twice. All three are needed together: -BaseUrl is where the installer is fetched from, -McpUrl is the API the bridge talks to, and the CA hash is what makes that fetch verifiable. Take the hash from sha256sum /etc/ipa/ca.crt on any enrolled host, or from IT, rather than trusting the copy printed here. Without -McpUrl the workstation is SSH-only and nothing MCP-related is installed.

The script downloads over TLS and that is the whole of the assurance: there is no signature and nothing to verify by hand. A host that serves these files and is compromised serves whatever it likes: SECURITY.md [SC1]. Nothing else on the workstation is modified.

No WSL2 at all and the install stalls? Once, elevated: wsl --install -d Ubuntu-24.04, launch it once to create your Linux user, reboot if asked, then re-run. The script is idempotent, so a second run is safe.

macOS

A Mac does not join the realm: there is no ipa-client-install for it, so this configures the Kerberos client and nothing more. The realm never learns the machine exists. Everything below is that configuration, either as one script or as the steps it runs.

cd "$(mktemp -d)"
curl --proto '=https' --tlsv1.2 -fsS __BASE__/setup-macos.sh -o setup-macos.sh

# Read it first if you like; --dry-run prints the plan and changes nothing.
sh setup-macos.sh \
    --domain __DOMAIN__ \
    --realm __REALM__ \
    --kdc __KDC__ \
    --dns-ip __DNS_IP__ \
    --ipa-user <your-ipa-username> \
    --base-url __BASE__ \
    --mcp-url __MCP_URL__ \
    --ca-sha256 <ca-sha256>

kinit <your-ipa-username>@__REALM__

Drop --ca-sha256 and the realm CA step is skipped, which is fine unless you need HTTPS to __MCP_URL__; kinit and ssh never use it. Drop --mcp-url and you get realm SSO without the bridge. Add --managed to register the bridge for every user on the machine rather than just you, which takes exclusive control of MCP configuration.

Use the hash IT gave you, not the one further down this page. That copy is a convenience for spotting an obvious mismatch, but it is served by the same infrastructure as the certificate, so on its own it checks that infrastructure against itself. If the two disagree, stop.

The rest of this section is what the script does, step by step. Read it if you want to understand the machine you are about to change, or follow it by hand if you would rather not run a downloaded script. It was worked out and proven on a live Mac.

Read this before you debug anything. The KDC line must be kdc = tcp/__KDC__, with the tcp/ prefix. macOS ships Heimdal, not MIT Kerberos, and Heimdal has no udp_preference_limit. Over UDP the KDC issues your ticket and the oversized reply is then dropped by any VPN with a small MTU, so the client tells you "unable to reach any KDC in realm" about a KDC that already answered. The error points nowhere near the cause. This one prefix is the difference between a working Mac and a lost afternoon.

# 1. Split DNS: send realm lookups to the realm's resolver.
sudo mkdir -p /etc/resolver
printf 'nameserver __DNS_IP__\n' | sudo tee /etc/resolver/__DOMAIN__ >/dev/null

# 2. Kerberos. Note "kdc = tcp/" below: macOS ships Heimdal, which has no
#    udp_preference_limit. Without the tcp/ prefix the KDC issues the ticket,
#    the oversized UDP reply is dropped on a small-MTU VPN, and the client
#    reports "unable to reach any KDC in realm" long after it was reached.
sudo tee /etc/krb5.conf >/dev/null <<'CONF'
[libdefaults]
    default_realm = __REALM__
    dns_lookup_realm = false
    dns_lookup_kdc = false
    rdns = false
    ticket_lifetime = 24h
    renew_lifetime = 7d
    forwardable = false

[realms]
    __REALM__ = {
        kdc = tcp/__KDC__
        admin_server = __KDC__
        default_domain = __DOMAIN__
    }

[domain_realm]
    .__DOMAIN__ = __REALM__
    __DOMAIN__ = __REALM__
CONF

# 3. SSH over GSSAPI. Delegation stays off on purpose: SECURITY.md [CL1].
mkdir -p ~/.ssh && chmod 700 ~/.ssh
cat >> ~/.ssh/config <<'CONF'
Host *.__DOMAIN__
    User <your-ipa-username>
    GSSAPIAuthentication yes
    GSSAPIDelegateCredentials no
CONF
chmod 600 ~/.ssh/config

# 4. Get a ticket. klist -v is the Heimdal spelling, not klist -f.
kinit <your-ipa-username>@__REALM__
klist -v

Then ssh anything.__DOMAIN__ with no password. Re-run kinit when the ticket expires, about once a day. klist -v prints the flags; klist -f is the MIT spelling and is not what this Kerberos understands.

forwardable is false, deliberately. A non-forwardable ticket cannot be delegated even by a client that asks to, which pairs with GSSAPIDelegateCredentials no above. Turn it on only if you are doing SECURITY.md [D1] on-behalf-of forwarding. For SSH it buys nothing and costs the stronger posture.

The realm CA is optional and most people do not need it. kinit and ssh do not use it at all: GSSAPI and host keys carry that. You need it only for HTTPS to __MCP_URL__. If you want it, fetch it, check the hash against the value IT gave you out of band (not from this page, which is served by the same infrastructure), and only then trust it:

curl -fsS -o /tmp/realm-ca.crt http://__KDC__/ipa/config/ca.crt
shasum -a 256 /tmp/realm-ca.crt          # must equal __CA_SHA256__
sudo security add-trusted-cert -d -r trustRoot \
     -k /Library/Keychains/System.keychain /tmp/realm-ca.crt

That fetch is plain HTTP, so the hash comparison is the entire check. If it does not match, stop and talk to IT rather than installing it anyway.

Optional: the MCP bridge

Only if you have been asked to run it, and only after the realm CA step above: the bridge speaks HTTPS to __MCP_URL__, and without the CA in the System keychain that fails with an opaque certificate error. python-gssapi ships macOS wheels for both Intel and Apple silicon, so this needs no compiler and no Xcode tools. The wheel links the system GSS.framework, the same Heimdal behind kinit, so the bridge reads the very ticket klist shows, on any macOS release.

# 5. MCP bridge. A per-user install: no sudo needed anywhere.
mkdir -p "$HOME/Library/Application Support/mcp-krb"
cd "$HOME/Library/Application Support/mcp-krb"
python3 -m venv venv
venv/bin/pip install --quiet gssapi
curl --proto '=https' --tlsv1.2 -fsS -o mcp-krb-bridge.py __BASE__/mcp-krb-bridge.py

# 6. Register it with Claude Code (kinit first, if you have not already).
claude mcp add --scope user internal-tools -- \
    "$HOME/Library/Application Support/mcp-krb/venv/bin/python3" \
    "$HOME/Library/Application Support/mcp-krb/mcp-krb-bridge.py" \
    __MCP_URL__

No claude CLI (desktop app only)? Add the same entry to ~/.claude.json under mcpServers, the shape shown in bridge/examples/mcp.json.example, with the two paths above as the command and first argument.

Honesty about how proven this is: the wheel linkage has been verified (it names the system GSS.framework and bundles nothing, so there is no second credential cache to fall into), but this path has not yet been exercised end to end against the MCP server from a Mac. The one genuinely untested step is a Heimdal SPNEGO initiator talking to the server's MIT acceptor, the same pairing every Mac that SSHes into the realm already uses. If a tool call fails where klist shows a valid ticket, tell IT: you are the first to run this leg.
