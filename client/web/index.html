Machine provisioning

Set your workstation up for Kerberos single sign-on against __REALM__.

Linux Windows macOS Artifacts

Linuxdefault

Enrols the machine in FreeIPA and installs the MCP bridge. After this you get a Kerberos ticket at login, and ssh works with no password anywhere in the realm. Ask whoever runs FreeIPA to run ipa host-add yourbox.__DOMAIN__ --random first: it prints the one-time password you paste below, and it is good for one enrolment only.

If /etc/ipa/default.conf already exists the machine is enrolled: skip the enrolment entirely and use the second block, which installs the bridge only.

Case 1: the machine is not enrolled yet

cd "$(mktemp -d)"
curl --proto '=https' --tlsv1.2 -fsS __BASE__/setup.sh -o setup.sh

sudo sh setup.sh \
    --base-url __BASE__ \
    --mcp-url __MCP_URL__ \
    --hostname=<the FQDN IT gave you> \
    --server=__KDC__ \
    --domain=__DOMAIN__ \
    --realm=__REALM__ \
    --password='<OTP>' \
    --unattended

Case 2: the machine is already enrolled

cd "$(mktemp -d)"
curl --proto '=https' --tlsv1.2 -fsS __BASE__/install-bridge.sh -o install-bridge.sh

sudo sh install-bridge.sh \
    --base-url __BASE__ \
    --mcp-url __MCP_URL__ \
    --managed

Both blocks download the script to a file and then run it, instead of piping curl into sh, so a truncated or interrupted download cannot half-execute as root. --proto '=https' pins the transfer to HTTPS so a redirect cannot silently downgrade it to plaintext.

TLS is the whole of the assurance on these bytes. There is no signature and no checksum file to verify. Once the machine is enrolled the scripts pin their own downloads to the realm CA at /etc/ipa/ca.crt and warn loudly if that pin ever falls back to the public trust store, but the first fetch above is ordinary public-CA TLS. Whoever controls the host serving these files decides what runs as root here: SECURITY.md [SC1]. If that is in your threat model, ship a signed package from an internal repo in your base image instead.

Extras: --skip-mcp enrols in FreeIPA only, leaving the bridge for later. Drop --managed from the second block to install the bridge without registering it machine-wide; the script then prints the claude mcp add line to run as yourself. Drop --unattended from the first block if you would rather confirm the enrolment interactively.

other platforms

Windows 11

Windows' built-in ssh.exe cannot read a Kerberos ticket, so the client runs inside WSL2. Open PowerShell as Administrator: installing the WSL distro needs it. If a distro already exists that step is skipped, but start elevated anyway so the run does not stop halfway.

One command, one file to download. The realm values below are already filled in for you, so the only thing to edit is your username.

# Run PowerShell as Administrator.
$base = "__BASE__"
iwr -useb "$base/setup.ps1" -OutFile setup.ps1

.\setup.ps1 -IpaUser <your-ipa-username> `
    -Domain __DOMAIN__ -Realm __REALM__ -Kdc __KDC__ `
    -BaseUrl __BASE__ -McpUrl __MCP_URL__ -CaSha256 __CA_SHA256__

That sets up all three pieces: Kerberos SSH through WSL2, VS Code Remote-SSH with remote.SSH.path pointed at a dispatcher so *.__DOMAIN__ goes through WSL while every other host keeps using the native Windows ssh, and the MCP bridge. One profile, both worlds, nothing to run afterwards.

Afterwards, in a new terminal: wsl kinit <your-ipa-username>@__REALM__, then wslssh host.__DOMAIN__. Your existing ssh, keys, host aliases and known_hosts are left untouched: the script adds wslssh rather than hijacking ssh. Tickets last 24 hours and renew with wsl kinit -R.

Take -CaSha256 from sha256sum /etc/ipa/ca.crt on an enrolled host, or from IT, rather than the copy printed on this page. It is what makes the download verifiable, and a hash read from the same page it is meant to verify proves nothing.

It also installs Firefox inside WSL. That is not a preference: Windows holds no Kerberos ticket, so a Windows browser can never answer a Negotiate challenge and will ask for your password forever. The one in WSL reads the same ticket your wslssh does, and appears in the Start menu like any other app.

Escape hatches, and not the normal path: -SkipVSCode leaves editor settings alone, -SkipMcp installs SSH only, -SkipFirefox leaves the browser out. All three are for machines that genuinely should not have those pieces.

The script downloads over TLS and that is the whole of the assurance: there is no signature and nothing to verify by hand. A host that serves these files and is compromised serves whatever it likes: SECURITY.md [SC1]. Nothing else on the workstation is modified.

No WSL2 at all and the install stalls? Once, elevated: wsl --install -d Ubuntu-24.04, launch it once to create your Linux user, reboot if asked, then re-run. The script is idempotent, so a second run is safe.

macOS

A Mac never joins the realm: there is no ipa-client-install for macOS, so this configures the Kerberos client and nothing more. Nothing is added to FreeIPA, so unlike a Linux box you need no host entry and no one-time password first.

Read this before you debug anything. The KDC line must be kdc = tcp/__KDC__, with the tcp/ prefix. macOS ships Heimdal, not MIT Kerberos, and Heimdal has no udp_preference_limit. Over UDP the KDC issues your ticket and the oversized reply is then dropped by any VPN with a small MTU, so the client tells you "unable to reach any KDC in realm" about a KDC that already answered. The error points nowhere near the cause. This one prefix is the difference between a working Mac and a lost afternoon.

The realm CA comes first, and that ordering is not cosmetic. Every host here presents a certificate signed by the realm's own CA, which a fresh Mac has never heard of, so HTTPS to this site fails until the CA is trusted. The certificate itself is fetched over plain HTTP, needing no trust, and the hash is what makes that safe: the first command below refuses to install anything whose SHA-256 does not match. The value is filled in for you, which is convenient and proves nothing on its own: this page comes from the same infrastructure as the certificate, so it would agree with a forgery just as readily. Compare it against the value your IT team gave you before you run it. On an already-enrolled machine, sha256sum /etc/ipa/ca.crt is the same check. Either spelling of that value works: the hash of the PEM file, which is what sha256sum /etc/ipa/ca.crt prints on an enrolled host, or the DER fingerprint a browser's certificate dialog shows, with or without its colons. They are different strings for the same certificate. Do not reach for curl -k to get past this. That would fetch a script you are about to run with sudo over a connection nothing has verified, which is the one thing SECURITY.md [SC1] promises never happens.

Nothing below is commented, deliberately. macOS uses zsh, and zsh does not treat # as a comment in an interactive shell unless interactive_comments is set, which it is not by default. Pasting a commented block gives you command not found: #. The commentary lives out here instead, so everything in a box can be pasted as-is.

__CA_BEGIN__
curl -fsS -o /tmp/realm-ca.crt http://__KDC__/ipa/config/ca.crt
echo "__CA_SHA256__  /tmp/realm-ca.crt" | shasum -a 256 -c - \
  && sudo security add-trusted-cert -d -r trustRoot \
       -k /Library/Keychains/System.keychain /tmp/realm-ca.crt

__CA_END__
cd "$(mktemp -d)"
curl --proto '=https' --tlsv1.2 -fsS __BASE__/setup-macos.sh -o setup-macos.sh

sh setup-macos.sh \
    --domain __DOMAIN__ \
    --realm __REALM__ \
    --kdc __KDC__ \
    --dns-ip __DNS_IP__ \
    --ipa-user <your-ipa-username> \
    --base-url __BASE__ \
    --mcp-url __MCP_URL__ \
    __CA_ARG__

kinit <your-ipa-username>@__REALM__

The && on the third line is load-bearing: a hash that does not match leaves the certificate untrusted, and the curl below it then fails rather than quietly proceeding. If you see a TLS error there, the CA step did not succeed; do not work around it.

Past that, the script does the lot: split DNS, Kerberos, SSH, the CA again (harmlessly, it is idempotent) and the MCP bridge. Add --dry-run to print the plan and change nothing; add --managed to register the bridge for every user on the machine rather than just you. Afterwards ssh anything.__DOMAIN__ needs no password, and kinit again when the ticket expires, about once a day. Use klist -v for the flags: klist -f is the MIT spelling and not what this Kerberos understands. VS Code needs no configuration here, because the remote.SSH.* settings on the Windows tab exist only to push ssh across the WSL boundary, and a Mac's own ssh already speaks GSSAPI.

By hand

The same thing without running a downloaded script, in six stanzas: 1 the realm CA, first for the reason above, 2 split DNS to the realm resolver, 3 the Kerberos client, 4 SSH over GSSAPI with delegation off (SECURITY.md [CL1]), 5 the bridge as a per-user venv needing no sudo, and 6 registering it, then a ticket. default_ccache_name is deliberately unset: macOS keeps the ticket in a session-wide cache, which is what lets an app launched from the Dock find it.

__CA_BEGIN__
curl -fsS -o /tmp/realm-ca.crt http://__KDC__/ipa/config/ca.crt
echo "__CA_SHA256__  /tmp/realm-ca.crt" | shasum -a 256 -c - \
  && sudo security add-trusted-cert -d -r trustRoot \
       -k /Library/Keychains/System.keychain /tmp/realm-ca.crt

__CA_END__
sudo mkdir -p /etc/resolver
printf 'nameserver __DNS_IP__\n' | sudo tee /etc/resolver/__DOMAIN__ >/dev/null

sudo tee /etc/krb5.conf >/dev/null <<'CONF'
[libdefaults]
    default_realm = __REALM__
    dns_lookup_realm = false
    dns_lookup_kdc = false
    rdns = false
    ticket_lifetime = 24h
    renew_lifetime = 7d
    forwardable = false

[realms]
    __REALM__ = {
        kdc = tcp/__KDC__
        admin_server = __KDC__
        default_domain = __DOMAIN__
    }

[domain_realm]
    .__DOMAIN__ = __REALM__
    __DOMAIN__ = __REALM__
CONF

mkdir -p ~/.ssh && chmod 700 ~/.ssh
cat >> ~/.ssh/config <<'CONF'
Host *.__DOMAIN__
    User <your-ipa-username>
    GSSAPIAuthentication yes
    GSSAPIDelegateCredentials no
CONF
chmod 600 ~/.ssh/config

mkdir -p "$HOME/Library/Application Support/mcp-krb"
cd "$HOME/Library/Application Support/mcp-krb"
python3 -m venv venv
venv/bin/pip install --quiet gssapi
curl --proto '=https' --tlsv1.2 -fsS -o mcp-krb-bridge.py __BASE__/mcp-krb-bridge.py

claude mcp add --scope user internal-tools -- \
    "$HOME/Library/Application Support/mcp-krb/venv/bin/python3" \
    "$HOME/Library/Application Support/mcp-krb/mcp-krb-bridge.py" \
    __MCP_URL__

kinit <your-ipa-username>@__REALM__
klist -v

No claude CLI (desktop app only)? Add the same entry to ~/.claude.json under mcpServers, the shape shown in bridge/examples/mcp.json.example, with the two paths above as the command and first argument. Note that the Claude Desktop chat app reads a different file and is not configured by either route.

Artifacts

Six files, flat, and that is the whole set. Nothing here is signed. There is no checksum manifest and no signature to check: transport is TLS and TLS alone, so whoever controls this host controls what runs on your machine. That trade is written up in SECURITY.md [SC1].
